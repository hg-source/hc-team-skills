# 면접준비 — 팀장 채용 면접 세팅

이력서와 실제 지원 공고(JD)를 바탕으로 후보별 질문, 잠정 AI 1차평가, PDF 뷰어가 있는 로컬 면접툴을 구성한다. 여러 명이면 후보별로 구분한다. 이력서의 외부 DB 저장은 이 스킬의 범위가 아니며, 다른 스킬 설치나 사내 시스템 접근이 없어도 동작해야 한다.

## 실행 환경과 최초 준비

- Node.js 18 이상, Claude Code, PDF를 읽을 수 있는 도구가 필요하다. 이 스킬의 Node 스크립트에는 추가 npm 의존성이 없다.
- 이 SKILL.md가 실제 설치된 디렉터리를 `SKILL_ROOT`로 삼는다. 현재 프로젝트 디렉터리라고 가정하지 않는다.
- 작업 요청을 받으면 먼저 아래 스크립트를 실행한다. 기본 작업 폴더는 사용자 홈의 `Documents/EGNIS 면접도구`이며, 출력되는 절대경로를 `INTERVIEW_DIR`로 사용한다.

```text
node "<SKILL_ROOT>/scripts/setup-interview-tool.mjs"
```

- 사용자가 기존 면접툴 폴더를 명시했다면 스크립트의 첫 번째 인자로 그 절대경로를 전달한다. 환경변수 `EGNIS_INTERVIEW_DIR`도 지원한다. 사용자의 환경변수나 설정 파일을 임의로 바꾸지 않는다.
- 최초 실행은 빈 `면접툴.html`과 `면접_시드.js`를 만든다. 재실행은 기존 시드·PDF·평가·질문을 보존한다. HTML이 달라졌을 때만 날짜가 붙은 백업 후 갱신한다.
- 후보 데이터는 설치된 스킬 폴더나 Git 저장소에 저장하지 않는다. HTML·시드·후보 PDF는 상대경로가 작동하도록 INTERVIEW_DIR에 함께 둔다.

## 1. 후보 서류 확보

- 사용자가 파일을 첨부하거나 경로를 주면 그 파일을 사용한다. 이름만 주면 사용자 홈의 Downloads와 INTERVIEW_DIR에서 이름이 일치하는 PDF를 찾는다. 추가 폴더는 사용자가 지정했을 때만 탐색한다.
- 파일명에서 이름·포지션이 명확하면 다시 묻지 않는다. 동명이인, 다른 직무, 파일 충돌이 있으면 경로·파일명을 보여주고 확인한다.
- 이력서·포트폴리오·지원서를 후보별로 묶어 INTERVIEW_DIR에 복사한다. 원본을 이동하거나 삭제하지 않는다. 같은 이름의 기존 파일이 다르면 날짜 백업 후 교체하거나 별도 이름을 사용한다.
- 자동 PDF 연결은 이름이 파일명에서 독립된 단어인 경우를 인식한다. 예: `홍길동 이력서.pdf`, `상품기획_홍길동_이력서.pdf`. 모호하거나 이름이 없는 파일은 `_pdfs_홍길동.json`에 실제 로컬 파일명 배열을 명시한다.
- PDF를 읽지 못하면 보유한 PDF 읽기 도구를 사용한다. 도구가 없으면 텍스트 제공 또는 로컬 추출 도구 설치 승인을 요청한다. 파일명만으로 이력·성과를 만들지 않는다.

## 2. 실제 JD와 직무 맥락 확인

사용자가 준 JD 파일·텍스트·공고를 우선한다. 이그니스 공개 채용 공고는 제공 스크립트로 찾을 수 있다. 이력서나 후보 개인정보를 웹으로 전송하지 않는다.

```text
node "<SKILL_ROOT>/fetch-jd.mjs" "상품기획 팀장" --division 헬스케어 --cache-dir "<INTERVIEW_DIR>/jd-cache"
node "<SKILL_ROOT>/fetch-jd.mjs" --list --json
node "<SKILL_ROOT>/fetch-jd.mjs" --id <공고번호> --cache-dir "<INTERVIEW_DIR>/jd-cache"
```

- 캐시 우선이다. stderr의 `[cache]` / `[web]`, 공고 URL, 저장 시점을 확인한다. 다른 공고이거나 최신 내용 확인이 필요하면 `--refresh`를 사용한다.
- 여러 공고가 맞으면 임의 선택하지 말고 정확한 공고번호로 좁힌다. 조회 실패 시 제공된 JD를 요청하거나, 사용자에게 한계를 밝힌 잠정 질문으로 진행한다.
- JD 핵심업무·필수요건·우대요건에서 역량 4~6개를 도출한다. 다른 직무의 요건을 전용하지 않는다.
- 팀 규모·조직도·보고라인·후임 채용 여부·사내 실적은 하드코딩하지 않는다. 사용자가 제공한 최신 자료만 보강 맥락으로 사용하며, 없으면 확인 필요로 둔다.

## 3. 질문·평가 작성

질문을 만들기 전에 [면접질문 고도화 가이드](references/면접질문-고도화-가이드.md)를 읽는다. 파일 저장 시에는 [출력 규격](references/output-spec.md)을 따른다.

후보마다 다음 파일을 만든다.

- `질문_<이름>.txt`: 전체 약 30문항. 핵심성과 1개를 배경·진단·판단·실행·손익·본인기여·회고로 파고드는 5~6문항, 직무별 맞춤 질문, 공통 질문 약 10개. 모든 질문에 `의도:`를 붙인다.
- `_position_<이름>.txt`: 실제 지원 직무 한 줄. 직무를 임의로 브랜드/마케팅 팀장으로 가정하지 않는다.
- `_ai_<이름>.json`: 이력서·JD 근거와 미확인 항목을 구분한 잠정 1차평가. 평가를 원치 않으면 만들지 않는다. 이전 평가가 있으면 삭제 대신 날짜 백업으로 옮겨 시드에서 제외한다.
- `_pdfs_<이름>.json`: 자동 연결이 모호할 때만 만드는 로컬 PDF 파일명 배열.

같은 포지션의 후보에게는 공통 질문·순서·행동기준을 같게 유지한다. 성과 수치의 기준선·기간·측정 출처·본인 기여·비용·반증을 확인한다. 성별·나이·가족관계 등 직무와 무관한 개인 특성을 추정하거나 평가 근거로 삼지 않는다. AI 점수·PASS/보류/FAIL은 잠정 참고값이며 최종 채용 판단은 면접관이 한다.

주요 경력은 시작월·종료월·포함월 기준 근속기간을 함께 표시한다. 불명확하면 산정 필요로 표시한다.

```text
node "<SKILL_ROOT>/scripts/career-duration.js" 2021.04 2023.12
```

## 4. 시드 생성과 검증

```text
node "<SKILL_ROOT>/build_seed.js" "<INTERVIEW_DIR>"
node "<SKILL_ROOT>/scripts/verify-seed.cjs" "<INTERVIEW_DIR>/면접_시드.js" "<대상 후보 이름>"
```

- 입력을 모두 검증한 후 시드를 쓴다. PDF 누락, 잘못된 AI JSON, 질문/의도 누락이면 원인을 해결하고 재실행한다. 실패를 성공으로 안내하지 않는다.
- 기존 시드는 변경될 때만 날짜 백업한다. 동일 입력은 같은 시드 버전이므로 불필요하게 면접 상태를 갱신하지 않는다.
- 여러 후보라면 검증 명령 뒤에 이름을 각각 추가한다. 질문 수·PDF 연결·직무·AI 포함 여부를 실제 출력으로 확인한다.
- 사용자가 이미 인터뷰한 질문을 수정할 때는 먼저 면접툴의 JSON 내보내기로 기록을 보존하도록 안내한다. 동일 질문의 메모·체크와 기존 평가 상태를 보존하며, 바뀐/제외된 질문의 이전 기록도 보관한다.

## 5. 완료 안내

실제 생성된 `면접툴.html`의 절대경로를 제공하고, 브라우저로 열거나 기존 창에서 새로고침하도록 안내한다. 후보 탭·좌측 PDF·우측 질문과 평가를 확인한다. 시드 검증만 했다면 실제 브라우저 표시까지 검증했다고 말하지 않는다.

- 면접 메모·점수는 해당 브라우저의 로컬 저장소에 남는다. 다른 PC/브라우저로 자동 공유되지 않으며 보존하려면 JSON 내보내기를 사용한다.
- PDF 자동 표시가 브라우저 정책으로 막히면 툴의 PDF 추가 버튼으로 같은 로컬 파일을 선택한다.
- 로컬 파일을 표시하는 HTML 자체에는 업로드 기능이 없다. 다만 Claude Code가 서류를 읽는 과정은 사용 중인 AI 서비스의 데이터 처리 정책을 따른다.
- 스킬 수정은 정본에서만 수행한다. 설치된 사본·PDF·질문·평가·JD 캐시를 공개 저장소에 올리지 않는다.
